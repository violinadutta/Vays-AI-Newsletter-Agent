1What this system does

Marketing at Vays used to read partner blog posts by hand, summarise them, rewrite them into customer-facing copy, format the HTML, and send the result. This platform does that end to end — and can now do it unattended, once a month, with a human approving the send.

1.1 The pipeline

Everything the platform does is one pipeline. The manual and automated modes run the same pipeline; they differ only in who starts it and who clicks send.

1.2 Two ways to run it

Manual — the dashboard

A person pastes blog URLs into Generate Newsletter, reviews and edits the generated copy on Campaign Preview, then sends. Full control, used for one-off or special campaigns. This is milestones M1–M9.

Automated — the agent

A background worker checks the Vays blog on a schedule, generates a newsletter from any new post, emails management a secure approval link, and sends to the whole list on the 3rd Wednesday of the month. This is M10.

Both write to the same database and appear in the same Campaign History. The automated mode is simply the manual mode with a scheduler and an email-based approval step in front of it.

1.3 The three constraints that shaped everything

ConstraintWhat it means in the code
Open-source LLM only The model must be open-weight; the host need not be. Groq serves only open-source models, so openai/gpt-oss-120b (Apache 2.0) satisfies this more cleanly than self-hosting would. See D-2.
Zero local inference No model, weights, or inference runtime ever runs on the developer machine. Machine-enforced: scripts/check_no_local_inference.py fails the build if torch, transformers, ollama, vllm or friends appear in any requirements file or import. It runs first in CI.
Handover-ready Another developer must clone, configure and run this on a different Windows PC from the documentation alone. That is what this document is for.

2Quick start on a fresh machine

Target: a working dashboard in about ten minutes, assuming Python is installed.

2.1 Prerequisites

Python3.11 – 3.14 (developed and verified on 3.14.3, Windows 11 AMD64)
OSWindows 10/11 primary. The code is pathlib-based and CRLF-safe; Linux works and is covered by CI, but run.bat is Windows-only.
RAMAny. All inference is remote — this runs on an 8 GB laptop with no GPU.
NetworkOutbound HTTPS to api.groq.com, the blog, and your mail provider.
Not neededNode.js, Docker, Redis, a GPU, or any paid service beyond a mail provider.

2.2 The six commands

# 1 — get the code and a virtual environment
git clone <repo-url> vays-newsletter-ai
cd vays-newsletter-ai
py -3.12 -m venv .venv
.venv\Scripts\activate

# 2 — install exactly the versions that were tested
pip install -r requirements.lock.txt

# 3 — configuration
copy .env.example .env
python -c "import secrets; print(secrets.token_urlsafe(48))"
#    paste that into APP_SECRET_KEY=  in .env, then add GROQ_API_KEY=

# 4 — create the database (12 tables, 5 migrations)
alembic upgrade head

# 5 — create the first login. No default password exists anywhere.
python -m scripts.create_user

# 6 — run
run.bat            # → http://localhost:8501
Use the lockfile requirements.lock.txt pins all 132 packages for a byte-identical install. requirements.txt holds the loose ranges and is what you edit when adding a dependency; regenerate the lock with pip freeze afterwards.

2.3 What run.bat checks before it starts

A fresh machine fails in four predictable ways, so the launcher checks for each and names the fix rather than showing a stack trace:

CheckWhy it exists
Virtual environment existsOtherwise streamlit resolves to a global install or nothing.
.env existsStartup would fail on a ConfigurationError with no clue that a file is simply missing.
Migrations appliedA schema behind head produces confusing OperationalErrors at first click, not at boot.
At least one user accountA login screen with no accounts is a dead end. This check is the difference between a two-minute start and an hour lost.

2.4 Running without the agent

run.bat starts only the dashboard. The automation is a separate process and is off by default (AGENT_ENABLED=false). Section 10 covers starting it. This separation is deliberate — see §3.3.

3.3 Two processes, not one

This is the single most important operational fact in the document.

Why separate Streamlit re-executes app.py top to bottom on every click, and a Streamlit session ends when the browser tab closes. A scheduler living inside that model would be restarted constantly, would run once per open tab, and would stop when the last tab closed. A separate process gets one clock, one instance, and a lifetime independent of anyone's browser.

3.4 External dependencies at runtime

ServiceRequired?Used for · failure behaviour
Groq APIrequired All generation. Failures raise typed errors (LLMRateLimitedError, LLMTimeoutError); a circuit breaker opens after repeated failures so a dead endpoint fails fast instead of hanging every request.
Mail providerrequired to send SMTP (Gmail) or Brevo. console writes .eml files to data/outbox/ and sends nothing — the safe default.
vaysinfotech.comagent only Blog discovery. Unreachable → the discovery job logs and returns; the next run retries.
ngrokoptional Only to make approval links clickable from outside the LAN. Absent → links fall back to http://localhost:8501, which works fine when approving from the same machine.

5Timing — exactly what is calculated when

Three independent clocks, and they are frequently confused. Discovery cadence is not send frequency; the dispatch poll is not the send time. Only the schedule plus max_in_flight decides how often a customer receives mail.

5.1 The three clocks

ClockDefaultSettingWhat it actually controls
Discoveryevery 6 hAGENT_DISCOVERY_INTERVAL_HOURS How soon after publication a new blog post is noticed. Raising it does not send more email.
Dispatch pollevery 5 minfixed in agent_worker.py How precisely the send lands on 11:00. A 5-minute poll means a send fires by 11:05 at the latest.
Send schedule3rd Wed, 11:00AGENT_SEND_* (4 vars) The only clock that decides when customers get mail.

5.2 How the send moment is computed

Settings.next_send_after(approved_at) in config/settings.py answers one question: given that a human approved at time T, what is the earliest legal moment to send? For the monthly schedule:

  1. Take the month of T in AGENT_TIMEZONE (default Asia/Kolkata).
  2. Find the 3rd Wednesday of that month via _nth_weekday_of_month() — walk to the first Wednesday, add 14 days.
  3. Set the clock to AGENT_SEND_TIME (11:00).
  4. If that instant is already past, roll forward with _add_months(+1) and repeat.

The dispatch job then simply asks now >= next_send_after(approved_at). Approving early is therefore always safe: approval never sends, it only makes a campaign eligible.

5.3 Why max_in_flight exists

A bug worth understanding before you change any timing setting "One newsletter per month" was first implemented as max_posts_per_run = 1. That caps each run, not the month — and with discovery running every six hours, a backlog of blog posts produced a queue of campaigns that all became due on the same 3rd Wednesday. This happened: nine newsletters went out within two minutes on 14 August. The fix is max_in_flight = 1: the agent refuses to start any new work while a campaign is still unsent. Frequency is now bounded by the pipeline, not by the discovery cadence — which means discovery can safely run as often as you like.

5.4 Changing the schedule

# .env — or Settings → Agent in the dashboard, which needs no restart
AGENT_SEND_SCHEDULE=monthly   # monthly | daily
AGENT_SEND_WEEKDAY=wednesday
AGENT_SEND_WEEK_OF_MONTH=3    # 1-5; ignored when schedule=daily
AGENT_SEND_TIME=11:00         # 24-hour HH:MM, anchored regex — "9:00" is rejected
AGENT_TIMEZONE=Asia/Kolkata

The dashboard renders the result in plain English via describe_schedule() ("3rd Wednesday of each month at 11:00 IST"), so a mis-set field is visible before it matters. AGENT_SEND_TIME is validated by an anchored regex rather than time.fromisoformat, which accepts 24:00 and silently means midnight.

Migrations

alembic upgrade head          # apply everything (this is what run.bat checks)
alembic revision --autogenerate -m "add x"   # then READ the generated file before applying
alembic downgrade -1          # step back one
alembic current               # what the database is on now
SQLite and ALTER TABLE SQLite cannot drop or alter a column in place; Alembic emulates it by rebuilding the table. Autogenerate handles the common cases, but always read the generated migration before running it against a database with real campaign history — and take a copy of data/newsletter.db first. It is one file; copying it is the entire backup procedure.

8Configuration

8.1 Two layers (D-24)

Configuration has a bottom layer and a top layer, and both matter for different reasons.

8.2 The secret rule, as a mechanism

SettingsService._validate_registry() runs at import time and raises if any registered field is a SecretStr. Adding llm.api_key to the editable registry therefore fails the build, not code review. That converts D-19 ("secrets stay in .env") from a convention a future developer could break into an invariant they cannot.

Three further properties make live editing safe rather than merely convenient:

  • validate_assignment=True on every settings section, so an edit runs the same validators as startup. A rejected value leaves the old one in place — the app is never left holding a config it could not have booted with. Verified: temperature=99 is refused and 0.7 survives.
  • The stored value is the normalised one, read back off the model after assignment. https://host/v1/ persists as https://host. Storing raw input would leave the database and the running process disagreeing about the endpoint — on this page of all pages.
  • Live mutation, not a rebuild. Every holder of get_settings() sees the change because the object is mutated in place. This only works because factories call get_settings() per operation instead of caching a provider — an invariant of other modules, so a test class asserts it. If someone later caches a provider, those tests fail rather than the feature silently doing nothing.

9Swapping things out

Everything below was designed to be replaceable, and most of these have already been done once for real. Each entry gives the reason you would do it, the exact steps, and what to run afterwards to know it worked.

1 config line

9.1 The LLM model

Why: cost, quality, a faster model, or replacing gpt-oss-120b if Groq retires it.

LLM_MODEL=openai/gpt-oss-20b     # smaller, faster, cheaper on TPM
# or a Qwen / Llama model Groq serves

The one trade-off. Only the gpt-oss family supports strict: true schema enforcement, which is what makes D-3 a guarantee rather than a hope. Switching to a Qwen or Llama model still works — supports_guided_json becomes False and the provider falls back to a repair-retry loop — but JSON validity becomes probabilistic instead of guaranteed. Weigh that before switching.

Verify: Settings → Test Connection (expect healthy plus a latency figure), then generate one real newsletter and confirm it validates on the first attempt.

1 class + 1 default

9.2 The LLM host

Why: moving off Groq entirely — to Together, Fireworks, an internal vLLM server, or anything OpenAI-compatible.

  1. If it is OpenAI-compatible, set LLM_PROVIDER=hosted and point LLM_BASE_URL at it. No code at all.
  2. If it is not, add a class in modules/ai/ implementing LLMProvider (three members: complete(), health_check(), supports_guided_json), then register it in modules/ai/factory.py::create_provider().
  3. Add the literal to LLMSettings.provider in config/settings.py.

This has been done for real. The Colab→Groq migration (D-21) cost exactly one class and one config default — no service, page, or test outside modules/ai/ changed. That is the strongest evidence the seam is real.

Verify: pytest tests/unit/test_ai_providers.py, then Test Connection, then one live generation.

1 config line

9.3 The email provider

Why: Gmail's ~500/day limit, moving to a real ESP, or going quiet for testing.

consoleWrites .eml to data/outbox/. Sends nothing. Use for any test.
smtpGmail or any SMTP host. Gmail needs an App Password, not the account password.
brevoAPI. 300/day permanent free tier; combines transactional and marketing.

For a provider that is none of these: implement EmailProvider in modules/email/ and register it in create_email_provider(). Reuse build_mime_body() so the CID logo keeps working.

Assert the provider in any script that can send A script of mine assumed EMAIL_PROVIDER=console without checking. .env had been switched to smtp, so three "preview" calls went to Gmail for real. The address was RFC-2606 undeliverable so nobody received anything, but it consumed quota and generated bounces. Every send-capable script now asserts the provider first. Keep that habit.
new HTML file

9.4 Email templates

Why: a rebrand, a new layout, or a seasonal variant.

  1. Copy templates/email/classic.html to a new name in the same directory.
  2. Keep the Jinja2 variables and the compliance block — the unsubscribe link and postal address are what guard 4 checks for. Removing them means the template can never send.
  3. Use table-based layout with inline-safe CSS. Node is not installed, so MJML was dropped (D-23); hand-authored table HTML is the source of truth.
  4. It appears in the Preview page picker automatically — the picker lists the directory.
Do not put non-newsletter templates in templates/email/ approval_request.html was placed there and, sorting before classic, silently became the default newsletter template and broke the Preview page. Internal templates live in templates/internal/ for exactly this reason.
1 URL + driver

9.5 The database

Why: more than one concurrent writer, a hosted deployment, or backup requirements SQLite cannot meet.

pip install psycopg[binary]
DATABASE_URL=postgresql+psycopg://user:pass@host:5432/vays_newsletter
alembic upgrade head          # builds the schema fresh on Postgres

Everything is SQLAlchemy 2.x with no raw SQL and no SQLite-only types, so the ORM layer carries over unchanged. Two things to check:

  • The WAL and foreign_keys pragmas in database.py are SQLite-specific. They are applied on connect and are harmless elsewhere, but read that function before you move.
  • Migrating existing data is a separate exercise from creating the schema. For a fresh Postgres, alembic upgrade head is genuinely all of it.

Verify: the full integration suite runs against the new URL — pytest tests/integration.

1 class

9.6 The blog source

Why: Vays moves off WordPress, or you want to monitor OEM partner blogs instead of (or as well as) the Vays blog.

  1. Point AGENT_BLOG_URL elsewhere. WordPress REST is tried first, RSS second — most blogs need nothing more.
  2. For a site with neither: implement DiscoverySource in modules/discovery/ — one method, fetch() -> list[DiscoveredPost] — and add it to build_sources().

Always populate external_id if the source has a stable identifier. dedupe_key() prefers it over the URL, so a changed slug does not resurface a post that has already been sent.

Verify: python agent_worker.py --once with EMAIL_PROVIDER=console, then check the discovered_posts table.

1 env var

9.7 Public hosting for approval links

Why: today the approval link points at localhost or a rotating ngrok URL, so it only works from the machine running the dashboard. This is the change that makes it work from a manager's phone.

# development — no configuration, tries ngrok then falls back
AGENT_APP_BASE_URL=auto

# production — one line, and every generated link follows
AGENT_APP_BASE_URL=https://newsletter.vaysinfotech.com

Everything that builds a link routes through resolve_base_url(), so this single variable is the whole migration. Nothing else needs to change.

Current state ngrok is installed but has no authtoken configured and no reserved domain, so its URL rotates on every restart. Claiming a free static domain is worth ten minutes if approval-from-phone matters before a real domain exists.
additive

9.8 Authentication

Why: company SSO, or moving off self-managed accounts.

The documented upgrade path is to replace AuthService.authenticate() with an OIDC/SAML exchange while keeping the rest of the interface. UserRole and the users table stay as the authorisation layer; only the identity check changes.

D-15 chose ~160 auditable lines in core/auth.py over an unvetted third-party package on the security boundary, precisely so this file could be read in full at handover and replaced deliberately.

edit YAML

9.9 Prompts

Why: tone, length, structure, or fixing something the model keeps getting wrong.

Prompts are versioned, never edited in place (D-6). Copy prompts/newsletter_compose/v1.1.0.yaml to v1.2.0.yaml and change that. Every campaign records the prompt version that produced it, so old campaigns still resolve their original prompt and remain reproducible.

Shared fragments live in prompts/_shared/: human_voice.md, length_rules.md, system_persona.md, untrusted_input_rules.md. Editing one changes every prompt that includes it — which is usually what you want for a voice change.

Two lessons that cost real debugging

  • State limits as hard limits. "approximately 60 characters" overshot every time. MAXIMUM 60 characters (this is a hard limit, not a target) landed in range on the first try.
  • A prompt instruction is not a guarantee. v1.0.0 said "give each story a short bold heading"; the field is plain text, so the model emitted **Heading** and the asterisks reached the customer. Fixed at both ends — v1.1.0 bans markdown explicitly, and _split_paragraphs converts a whitelist of markdown to real HTML as a safety net. Order is the security property: each paragraph is escaped first, then our own tags are inserted into the escaped string, so the safety net cannot become an injection hole.

Verify: python scripts/validate_prompts.py (checks schema and the max_tokens floor), then generate against a real article and read the output.

10.5 Routine tasks

Back up

copy data\newsletter.db backups\newsletter-2026-08-18.db

SQLite is one file. Copy it. In WAL mode, prefer copying while nothing is writing, or use sqlite3 data/newsletter.db ".backup backups/x.db" for a consistent snapshot.

Make the agent forget discovered posts

Clearing discovered_posts makes the agent treat every existing blog post as new. That is occasionally what you want (a fresh start) and usually not (it will regenerate old content). Take a backup first, and remember max_in_flight is what stops a re-discovered backlog becoming a flood of email.

Change who receives newsletters

Recipients page: upload a CSV (appends — it does not replace), paste addresses, or remove individuals. Removal deactivates rather than deletes, so past campaign history still resolves. Suppressed addresses stay suppressed even if re-uploaded.

Change who approves

AGENT_APPROVAL_EMAIL, or Settings → Agent. Takes effect on the next approval request; already-issued tokens are unaffected.

11.1 Test principles that were learned, not assumed

  • A coverage percentage hides a zero. generation_service.py — the orchestrator every generation flows through — had 0% coverage while the suite reported 90% overall. It is now 100%, tested with a stub engine rather than MockProvider so each failure mode can be provoked directly. This was the fourth instance of the same dead-code/untested-core pattern (app_logs, settings, set_password, then this). Grep for repositories with no production caller before assuming a module works.
  • Synthetic fixtures do not exercise token budgets. article_summary at 1024 tokens passed on a synthetic article and failed on a real one.
  • Tests must not touch the network or real data. Two tests were caught hitting the live blog and the real Groq API, and one read the developer's actual recipients directory. Fixtures now stub discovery and point at temp directories.
  • A test must discriminate the bug. My first health-check test passed against both the broken and fixed code because the mock provider is healthy either way. Rewritten around "configured but unhealthy", which is the case that actually differed.
  • SQLite returns plain str for enum columns. StrEnum compares equal but not identical, so assert with ==, never is.
  • AppTest.from_function re-executes the function's source, so a closure over an outer variable is silently lost — pass values via args=. The first test_pages.py asserted on pages it never rendered and would have passed against a UI that crashed on every click.

11.2 CI details worth keeping

  • pip-audit is continue-on-error and therefore advisory — a green tick does not mean clean. Read its output.
  • A dedicated job greps full git history for gsk_ and xkeysib-, because a secret deleted in a later commit is still leaked. Verified: history is clean and .env was never tracked.
  • The suite is also run under CI conditions (no .env, environment variables only) to prove the workflow configuration is right rather than plausible.
  • Every internal documentation link is checked by a script.

12.2 Input handling

  • SSRF guard on every URL. resolve_public_addresses() refuses loopback, link-local and RFC-1918 ranges — so a pasted http://169.254.169.254/ cannot make the server fetch cloud metadata.
  • Scraped text is untrusted input. prompts/_shared/untrusted_input_rules.md instructs the model to treat article content as data, not instructions.
  • Escape first, then insert. The markdown safety net escapes each paragraph before inserting our own tags into the escaped string, so it cannot become an HTML-injection hole.
  • Approval tokens — random, hashed at rest, single-use, expiring, campaign-scoped (§4.3).

12.3 Sessions

A browser refresh starts a new Streamlit session, so session_state is empty even though nobody signed out. ui/session.py restores the session from a cookie carrying the same HMAC-signed token the login issues. Three checks run before it is honoured:

  1. The signature verifies against APP_SECRET_KEY. A forged or tampered cookie is indistinguishable from a missing one.
  2. The token has not expired — 12 hours, carried inside the payload.
  3. The account still exists and is active. This is the check the token cannot make for itself: without it, deactivating someone would leave them signed in for up to twelve more hours.

The role that is honoured comes from the database, not from the token, so a stale cookie cannot preserve a privilege that has since been revoked. A cookie that fails any check is cleared, so the browser stops presenting something that will never work again. Eleven tests cover these paths.

A deliberate distinction from D-15 extra-streamlit-components (Apache-2.0) is used purely as cookie storage — it writes and reads an opaque string. Every security property stays in core/auth.py. That is why this is compatible with D-15, which refused streamlit-authenticator because that package would have owned authentication itself. A cookie jar owns nothing.
Known limitation The cookie is written from the browser side and therefore cannot be HttpOnly. That is inherent to setting cookies from Streamlit, not a shortcut. It is acceptable on a LAN-internal tool; if this app is ever exposed publicly, revisit it — the mitigation is a server-side session store, or terminating auth at a reverse proxy.

12.4 Roles

Two roles. Editor can generate, edit and send. Admin adds settings editing and user management. Password change re-authenticates first, so it runs the lockout counter and cannot be used to brute-force from inside a session. Self-deactivation is refused rather than warned about — the only admin locking themselves out has no way back in.
